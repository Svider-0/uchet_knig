## 1. Цель и задачи
**Цель работы:** разработать кроссплатформенное консольное приложение для локального учёта книжной коллекции, соответствующее требованиям современной разработки на Python: чистая архитектура, типизация, покрытие тестами, контроль качества кода и документирование.

**Задачи, поставленные в ходе практики:**
1. Настроить систему контроля версий Git, создать структуру проекта согласно техническому заданию (папки `src/`, `tests/`, `data/`, файл `requirements.txt`).
2. Реализовать модель данных с использованием декоратора `@dataclass`, обеспечив строгую типизацию полей и значения по умолчанию.
3. Настроить взаимодействие с реляционной СУБД SQLite через встроенный модуль `sqlite3`: инициализация схемы таблиц, использование параметризованных запросов, безопасное управление соединениями.
4. Разработать слой бизнес-логики (CRUD-операции) и презентационный слой (форматированный вывод таблиц через библиотеку `tabulate`).
5. Создать интерфейс командной строки (CLI) на базе `argparse` с валидацией входных данных и централизованной обработкой ошибок.
6. Написать модульные и интеграционные тесты с использованием `pytest`, применяя фикстуры для изоляции, захват стандартного вывода и временные файловые системы.
7. Обеспечить полное соответствие кода стандарту PEP 8 с помощью статического анализатора `flake8`.
8. Подготовить техническую документацию (`README.md`) и развёрнутый отчёт, выполнить финальную сборку и публикацию проекта в Git-репозитории.

Все пункты технического задания выполнены в полном объёме. Приложение работает автономно, не требует внешних серверов и готово к демонстрации.

## 2. Архитектура и стек
### 2.1 Технологический стек
Проект построен на минимальном наборе зависимостей, где внешние библиотеки используются только для задач, не решаемых стандартной библиотекой Python оптимальным образом.

- **Python 3.10+**. Базовый язык разработки. Выбран за встроенную поддержку `sqlite3` и `dataclasses`, современный синтаксис аннотаций типов (например, `list[Book]`) и зрелую экосистему инструментов.
- **sqlite3**. Встроенный модуль для работы с реляционной БД. Обеспечивает транзакционность, поддержку ограничений (`UNIQUE`, `NOT NULL`) и хранение данных в одном файле без необходимости разворачивания сервера.
- **dataclasses**. Стандартный декоратор для моделирования сущностей. Автоматически генерирует методы `__init__`, `__repr__` и `__eq__`, значительно уменьшая количество шаблонного кода и повышая читаемость.
- **tabulate**. Внешняя библиотека для визуализации. Позволяет форматировать список объектов в читаемые ASCII-таблицы прямо в терминале с поддержкой Unicode и различных стилей оформления.
- **pytest**. Фреймворк для тестирования. Используется за лаконичный синтаксис, мощную систему фикстур (`tmp_path`, `capsys`), автоматическое обнаружение тестов и гибкие конфигурации.
- **flake8**. Инструмент статического анализа. Контролирует соблюдение PEP 8, отслеживает неиспользуемые импорты/переменные и проверяет цикломатическую сложность функций.

### 2.2 Структура модулей и взаимодействие
Архитектура проекта следует принципу разделения ответственности. Каждый слой решает строго определённую задачу, что упрощает тестирование и масштабирование.

**Уровень представления (CLI):**
- `main.py` отвечает за парсинг аргументов командной строки, маршрутизацию команд и вывод результатов пользователю.
- `view.py` содержит функцию форматирования списка книг в таблицу через `tabulate`.

**Уровень бизнес-логики:**
- `repository.py` реализует CRUD-операции, преобразует кортежи из БД в объекты `Book` и обратно, управляет транзакциями.

**Уровень данных:**
- `database.py` устанавливает соединение, настраивает `row_factory` для доступа к колонкам по имени и создаёт схему таблицы при первом запуске.
- `models.py` содержит чистую модель `Book`, описанную через `@dataclass`.

**Схема взаимодействия:**
```
CLI (main.py) → парсит команду
       ↓
Repository (repository.py) → формирует SQL-запрос
       ↓
Database (database.py) → исполняет запрос, возвращает курсор
       ↓
Models (models.py) → данные маппятся в Book
       ↓
View (view.py) → результат форматируется и выводится в консоль
```
Такая структура позволяет заменить `sqlite3` на другую СУБД или добавить графический интерфейс, не переписывая бизнес-логику и тесты.

## 3. Реализация ключевых функций
### 3.1 Модель данных и корректный маппинг типов
SQLite не поддерживает нативный логический тип `BOOLEAN`. Значения `True` и `False` сохраняются как целые числа `1` и `0`. При выборке данных драйвер возвращает их в виде `int`, что нарушает контракт типизации модели (`is_read: bool`). Проблема решена на уровне репозитория: перед созданием экземпляра `Book` значение явно приводится к булевому типу.

```python
# src/repository.py
def get_all_books(db_path: Optional[str] = None) -> list[Book]:
    conn = get_connection(db_path)
    try:
        rows = conn.execute(
            "SELECT id, title, author, year, isbn, is_read FROM books"
        ).fetchall()
        books = []
        for row in rows:
            data = dict(row)
            data["is_read"] = bool(data["is_read"])  # 0/1 → False/True
            books.append(Book(**data))
        return books
    finally:
        conn.close()
```
Это гарантирует, что бизнес-логика, CLI и тесты работают со строго типизированными объектами, а особенности хранения СУБД остаются инкапсулированными в слое доступа к данным.

### 3.2 Безопасные CRUD-операции и управление соединениями
Для защиты от SQL-инъекций все запросы используют позиционную параметризацию (`?`). Управление соединением вынесено в блок `try/finally`. Это критично для ОС Windows: если произойдёт исключение или процесс будет прерван, соединение гарантированно закроется, и файл `*.db` не останется заблокированным системой.

```python
# src/repository.py
def add_book(book: Book, db_path: Optional[str] = None) -> int:
    conn = get_connection(db_path)
    try:
        cursor = conn.execute(
            "INSERT INTO books (title, author, year, isbn, is_read) VALUES (?, ?, ?, ?, ?)",
            (book.title, book.author, book.year, book.isbn, book.is_read),
        )
        conn.commit()
        return cursor.lastrowid
    finally:
        conn.close()
```
Функция возвращает `cursor.lastrowid`, что позволяет клиентскому коду сразу получить идентификатор новой записи без выполнения дополнительного `SELECT`.

### 3.3 CLI-парсер с подкомандами
Интерфейс построен на `argparse` с использованием `add_subparsers`. Такой подход делегирует валидацию обязательных аргументов самому фреймворку, устраняя необходимость в ручных проверках `if/else` внутри обработчиков.

```python
# src/main.py
def parse_args(args: Optional[list[str]] = None) -> argparse.Namespace:
    parser = argparse.ArgumentParser(description="Система учёта книг (CLI)")
    subparsers = parser.add_subparsers(dest="command", required=True)

    p_add = subparsers.add_parser("add")
    p_add.add_argument("--title", required=True)
    p_add.add_argument("--author", required=True)
    p_add.add_argument("--year", type=int, required=True)
    p_add.add_argument("--isbn", default="")
    p_add.add_argument("--read", action="store_true")
    return parser.parse_args(args)
```
Параметр `required=True` гарантирует, что вызов программы без указания подкоманды немедленно завершится с кодом возврата `2` и справкой, что соответствует стандартам поведения консольных утилит.

## 4. Тестирование и отладка
### 4.1 Стратегия проверки работоспособности
Проект покрыт тремя уровнями автоматизированных тестов:
1. **Модульные тесты (`test_database.py`)**: проверяют корректность создания файла БД и наличие таблицы `books` в системной таблице `sqlite_master`.
2. **Интеграционные тесты (`test_repository.py`)**: покрывают полный цикл добавления, чтения, обновления и удаления записей, а также проверяют корректность вывода таблицы через захват `stdout`.
3. **Тесты CLI (`test_main.py`)**: валидируют парсинг всех поддерживаемых команд, проверяют типы преобразованных аргументов и реакцию на некорректный ввод.

Запуск выполняется командой `pytest tests/ -v` из корня проекта. Все тесты изолированы и не влияют на рабочую базу данных.

### 4.2 Изоляция окружения тестов
Для предотвращения конфликтов и побочных эффектов используется встроенная фикстура `pytest` под названием `tmp_path`. Она создаёт уникальную временную директорию для каждого тестового случая. База данных инициализируется внутри этой директории, а после завершения теста автоматически удаляется сборщиком мусора Python и pytest. Вывод в консоль проверяется через фикстуру `capsys`, которая перехватывает `stdout` и `stderr` без реального вывода на экран.

```python
# tests/test_repository.py
@pytest.fixture
def test_db(tmp_path):
    db_file = tmp_path / "test_books.db"
    init_db(str(db_file))
    return str(db_file)
```

### 4.3 Основные ошибки и методы их устранения
В процессе разработки были выявлены и устранены следующие проблемы:

- **Проблема:** `AssertionError: assert 1 is True` в тестах на обновление статуса.  
  **Причина:** SQLite возвращает целочисленное значение (`1`), а тест ожидает строгий булев тип.  
  **Решение:** Добавлено явное приведение типа `bool(data["is_read"])` в функции выборки репозитория.

- **Проблема:** `PermissionError: [WinError 32] The process cannot access the file...`  
  **Причина:** При возникновении исключения в ходе выполнения SQL-запроса соединение с БД не закрывалось, что приводило к блокировке файла ОС Windows.  
  **Решение:** Все функции работы с БД обёрнуты в конструкцию `try/finally`, гарантирующую вызов `conn.close()` независимо от результата операции.

- **Проблема:** `ModuleNotFoundError: No module named 'src'` при запуске тестов.  
  **Причина:** Тесты запускались из поддиректории `tests/`, либо среда выполнения не видела корень проекта в `PYTHONPATH`.  
  **Решение:** Тестирование и запуск CLI выполняются строго из корня репозитория, используется команда `python -m pytest` и `python -m src.main`.

- **Проблема:** Предупреждения линтера `E501 line too long`.  
  **Причина:** SQL-запросы и многострочные строки документации превышали стандартный лимит в 79 символов.  
  **Решение:** Применён перенос строк с сохранением отступов, в конфигурацию `flake8` добавлен параметр `--max-line-length=100`, что является общепринятой практикой для современных Python-проектов.

После внесения правок `flake8` не выводит ошибок, а `pytest` показывает успешное прохождение 100% тестовых сценариев.
